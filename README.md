# Yeolo-AI

제로터치 초개인화 여행 플랫폼 **여로**의 AI 서버입니다. FastAPI와 LangChain/LangGraph로 취향 분석과 여행 코스 생성을 제공합니다.

## 개발 환경

- Python 3.14 이상
- [uv](https://astral.sh/uv)

## 설치 및 실행

```bash
uv sync --locked
```

[$.env]($.env)을 참고해 `.env`를 설정한 뒤 서버를 실행합니다.

```bash
uv run python -m app.main
```

- 서버: [http://127.0.0.1:8000](http://127.0.0.1:8000)
- API 문서: [Swagger UI](http://127.0.0.1:8000/docs)

## 테스트

```bash
# 전체 검증
bash .agents/hooks/test.sh

# 선택 검증
bash .agents/hooks/test.sh -- tests/test_gemini_parameters.py
```

## 여행 코스의 이동 시간

장소 사이 이동과 숙소 복귀에는 고정된 90분 기준을 적용하지 않습니다. 실제 조회한 이동 시간을 유지하며 다음 방문·식사 시간과 하루 일정에 체류 전체가 들어가는지 확인합니다. 일정에 맞지 않으면 다른 이동 수단을 비교하고, 가능한 일정끼리는 미확보 경로 수와 실제 총 이동 시간으로 순위를 정합니다. 숙소 복귀 시간은 내부 도착 시각이 있을 때 21시까지의 남은 시간으로 확인하며, 내부 시각이 없으면 임의의 출발 시각이나 구간 시간 상한을 만들지 않습니다.

## 여행 코스의 추천 이유와 방문 팁

`localize_display`는 장소명·이동 안내를 현지화한 뒤, 확정된 장소의 `reason`과 `memo`를 LLM으로 작성합니다. 입력은 검증된 장소 유형·주소와 해당 유형에 연결되는 사용자 취향 점수(4~5점), 같은 날 실제 앞뒤 방문의 검증된 유형으로 제한합니다. 같은 장소 조회에서 확보한 추가 유형도 설명 근거로 사용합니다. 장소명은 표시용 검색 명칭이며, 이름이나 모델의 사전 지식으로 시설·메뉴·역사 등의 사실을 추론하지 않도록 합니다.

방문 `reason`은 경험과 추천 맥락을 설명하는 2문장·100~180자, 방문 `memo`는 관찰·선택·조정 방법을 안내하는 2~3문장·140~240자를 목표로 작성합니다. 분량은 권장치이며, 근거가 적으면 짧은 문구를 허용합니다. 분량을 채우기 위한 반복이나 미확인 정보는 추가하지 않습니다. 이동 안내 `transportToNext.memo`의 정책은 동일합니다.

날짜별로 방문을 묶어 모든 날짜의 `작성 → 근거 검토`를 동시 처리 상한 없이 병렬 실행합니다. 한 날짜가 12개 방문을 넘으면 같은 날짜 안에서만 나눕니다. 예를 들어 날짜별 방문이 5곳인 3일 여행은 세 날짜의 문구를 동시에 작성하고, 각 날짜의 작성이 끝나는 즉시 다른 날짜를 기다리지 않고 별도 LLM 호출로 검토합니다. 모든 작업이 끝나거나 시간이 만료되면 날짜 전체의 반복 문구를 함께 검사하고 승인된 결과만 원래 슬롯에 적용합니다. 한 날짜의 실패는 다른 날짜의 승인된 문구를 버리지 않습니다.

긴 문구가 출력 상한으로 잘리지 않도록 출력 토큰 예산은 최대 16,000으로 설정합니다. 문구 생성의 별도 30초 제한은 없으며, 장소명·이동 안내의 한국어 번역이 끝난 시점에 전체 코스 요청에서 남은 시간을 사용합니다. 전체 요청 예산은 `COURSE_TIMEOUT_SECONDS`(기본 300초)이며, 종료 처리를 위한 기존 여유 시간은 유지합니다. SDK의 별도 호출 타임아웃 없이 하나의 공유 타이머로 모든 날짜의 작성·검토·대기·재시도를 제한하므로 단계나 재시도마다 시간이 새로 주어지지 않습니다. 날짜별 분리로 호출당 생성 분량이 줄지만 호출 수는 늘 수 있고, 실제 지연은 모델 응답 및 처리 제한에 따라 달라집니다.

기존 `course.candidates.generate` ABTO 경로를 사용하며 SDK 자동 재시도는 비활성화합니다. 첫 병렬 작업이 모두 끝나면 생성·응답 형식·근거 검토·문구 검사에 실패한 장소만 한 번 다시 작성·검토합니다. 동시 호출 한도 오류(예: 429)도 이 큐로 보내며, 재시도는 순차 실행해 진행 중인 첫 요청이나 다른 재시도와 겹치지 않도록 합니다. 성공한 장소는 재요청하지 않고 승인된 문구를 보존합니다. 대기와 재시도도 같은 전체 시간 예산을 사용하므로 시간 만료·요청 취소 시에는 추가 요청하지 않습니다. 장소·경로 조회는 추가하지 않습니다.

두 필드 모두 검토를 통과하고 ID·언어·새 숫자/URL·대표적인 미확인 정보·동일 문구 검사를 통과한 방문에만 적용합니다. **한 번 재시도해도 생성·검증에 실패하거나 시간 부족으로 재시도할 수 없으면 해당 방문의 `memo`와 `reason`은 빈 문자열입니다.** 고정 문구로 대체하거나 초안의 미검증 설명을 사용하지 않습니다. 관광지·숙소·공항 모두 같은 정책을 적용하며 장소·순서·시간·비용·이동 안내는 바꾸지 않습니다. `course_reasons.py`에는 취향 근거 선택만 남아 있습니다. 태그는 `course_tags.py`에서 검증된 공개 장소 분류에 따라 문화·자연·음식 등의 중립적인 분류명으로 구성하며, 현지화 실패 시에도 같은 분류를 사용합니다. 현재 상세 정보가 제한되어 장소 고유 시설이나 대표 메뉴는 설명할 수 없고, 의미 검토도 LLM이 수행하므로 모든 환각을 기계적으로 배제한다는 보장은 없습니다.


이동 안내 `transportToNext.memo`는 같은 경로 조회에서 확보한 실제 길찾기 지시·승하차 정류장·노선·방향을 사용합니다. 사용할 수 있는 정보가 없거나 안전하게 표시·번역할 수 없으면 `null`로 반환하며, 지도 앱 이용 등의 고정 안내문으로 대체하지 않습니다. 이때 확인된 이동 시간과 거리는 유지합니다. 후보 제안 스키마와 프롬프트는 사용하지 않는 `reason`을 생성하지 않습니다.

저장 결과 검사 도구 `scripts/verify_course_output.py`는 방문 `reason`·`memo`가 함께 비어 있으면 문구 미확보 경고로 처리하고, 한쪽만 작성된 경우에는 오류로 처리합니다. 이동 안내의 `null`은 허용하며, 장소·경로 수치·응답 필드·완료 이벤트 검사는 계속 적용합니다. 저장 결과만으로 문구의 사실성이나 내부 일정 적합성을 입증하지는 않습니다.


## 응답 언어

여행 코스와 취향 요약은 한국어만 생성합니다. 기존 `language` 요청 필드와 `Accept-Language` 헤더는 호환을 위해 유지하며, 유효한 외국어 코드도 허용하지만 내부 처리와 출력 언어는 항상 `ko`입니다. 외국어 번역 분기·문구·태그·취향 강도 라벨과 영어 대체 처리는 제거했습니다. 외국어 원본 장소명·길찾기를 한국어로 옮기는 기능과 검증된 장소 검색용 원어/영문명 조회는 유지합니다. 장소 ID·노선 코드·숫자·경로 사실은 번역으로 변경하지 않습니다.
